# Engineering Handbook

Универсальные правила разработки для работы с AI-агентом. Project-specific дополнения — в [`AGENT_PROJECT.md`](AGENT_PROJECT.md).

## Главный принцип

Самое правильное решение использует существующий API проекта, следует стилю соседнего кода и решает задачу минимальной необходимой сложностью.

Создавай новое только тогда, когда существующая модель действительно перестала справляться.

---

## Приоритеты

1. KISS и согласованность с проектом  
2. YAGNI  
3. SOLID (только если упрощает код)  
4. DRY (только при реальном дублировании ответственности)  
5. Расширяемость  

Багфикс ≠ архитектурный рефакторинг.

---

## Источник правды

При конфликте:

- Текущий код и соседние классы  
- [`AGENT_PROJECT.md`](AGENT_PROJECT.md) — пути, wiring, существующий API репозитория  
- `Docs/README.md`, `Docs/Roadmap.md`, документация модуля  
- Roadmap / SkillsRoadmap (что делать, не как)  
- Реализация в репозитории важнее любой абстракции  

Если код и спека расходятся — сначала опиши конфликт, не «чинить молча».

---

## Перед изменениями

- Прочитай правила репозитория и project appendix  
- Найди похожую реализацию  
- Определи слой системы (UI / Application / Domain / Data / Editor)  
- Проверь, существует ли уже нужный API  
- Убедись, что логика принадлежит модулю  

---

## Работа над задачей

### Fix / Implement

**0. Ожидаемое поведение**

- Таблица: источник → действие → результат  

**1. Воспроизведение**

- Flow вызовов  
- Lifecycle  
- Ownership состояния  
- Events / subscriptions  
- Execution order  
- Wiring / scene / prefab  

**Unity (если применимо)**

1. EditMode-тест — pure logic (math, FSM, resolver, парсеры)  
2. Play Mode — physics, aim, input, execution order  
3. Editor setup — missing `SerializeField`, prefab vs scene instance  
4. Не чинить `Find` / null-check в runtime, если корень в editor wiring  

**2. Корневая причина**

Исправляем причину, не симптом.

**3. Минимальный diff**

Используем существующий API.

**4. Границы изменений**

Что меняем / что не трогаем.

**5. Риски регрессии**

Что может сломаться рядом.

---

### Plan / Review

- Сначала анализ  
- Без кода, если не запрошен  
- Варианты + trade-off + рекомендация  

---

### Refactor

- Только отдельной задачей  
- Не смешивать с багфиксом  
- Сначала объяснение, потом изменения  

---

## Definition of Done

- [ ] Ожидаемое поведение подтверждено (Play Mode / EditMode test / лог)  
- [ ] Компиляция без ошибок; для сцен с editor validation — 0 errors  
- [ ] Diff минимален; несвязанные файлы не тронуты  
- [ ] Коммит и push — только по явной просьбе пользователя  

---

## Формат ответа агента

0. Ожидаемое поведение  
1. Корневая причина  
2. Минимальный фикс  
3. Что сознательно не трогаем  
4. Как проверить (конкретно: сцена, меню, клавиши, тесты)  

---

## Жизненный цикл и состояние

- Кто владеет состоянием  
- Кто подписан  
- Кто отписывается  
- Порядок уничтожения  
- Execution order  

Не маскируй проблемы null-check'ами, если правильнее исправить порядок подписки или wiring.

---

## Частые ошибки

- Создание нового слоя (Manager / Service / Helper) без явной пользы  
- Архитектурный рефакторинг внутри багфикса  
- Дублирование состояния  
- Polling вместо event / callback  
- Размазывание cleanup  
- Гадание без воспроизведения  
- Избыточные defensive checks вместо корневой причины  
- Новая абстракция вместо расширения соседнего класса или существующего static utility  

Static utility допустим, если одна чёткая ответственность и так уже сделано рядом.

## Нейминг

Имя = архитектура.

Если имя требует комментария — оно плохое.

### Общие правила

- Класс — существительное  
- Метод — глагол  
- Свойство — состояние  
- Событие — факт  

Избегай безымянных `Helper`, `Utils`, `ProcessData`, `HandleStuff`.

### Классы

`PlayerInventory`, `DamageCalculator`

### Интерфейсы

`IDamageSource`, `ISaveGameRepository`

### Методы

`LoadGame()`, `ApplyDamage()`

### Bool-методы

`IsAlive()`, `CanInteract()`

### Async

`LoadGameAsync()`, `SaveGameAsync()`

### Try

`TryGetTarget()`, `TryParseLevel()`

### Поля

`_health`, `_mainCamera`

### Свойства

`Health`, `CurrentWeapon`

### События

`PlayerDied`, `LevelLoaded`

### Корутины

`ReloadRoutine()`, `WaitRespawnRoutine()`

### Коллекции

`_enemies`, `_activeBuffs`

### Enum

`DamageType`, `MovementMode`

### Config

`WeaponConfig`, `CharacterStats`

## Архитектурные роли

Controller — flow orchestration  
Presenter — UI отображение  
Service — бизнес-логика  
Repository — хранение данных  
Factory — создание объектов  
Builder — сборка объектов  
Resolver — выбор варианта  
Coordinator — сценарии  
Session — временное состояние  
Action — одна операция  
State — FSM  
Context — зависимости  

Роль выбираем только если имя отражает реальную ответственность в проекте. Не вводим Service / Coordinator, если достаточно существующего Controller + Config.

## Главная цель

Не идеальная архитектура.

А:

- понятность  
- предсказуемость  
- согласованность  
- минимальная сложность
